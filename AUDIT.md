## F1. `-norestart`: штатный Ctrl+C считается крашем

**Severity: средне-высокая.** Ложная диагностика + противоречие документации.

В рестарт-ветке код 130 (SIGINT) явно отнесён к «чистому выходу», а в ветке без
рестарта фильтр `debugcore` знает только про `0` и `-debug`:

```bash
# hlds_run:300 — рестарт-ветка
if [[ $retval -eq 0 || $retval -eq 130 ]]; then

# hlds_run:141 — debugcore
if [[ $exitcode -eq 0 || $DEBUG -eq 0 ]]; then
    if [[ $exitcode -ne 0 ]]; then log_message "Server crashed, but debug mode is OFF."; fi

# hlds_run:325 — ветка без рестарта, 130/143 не отфильтрованы
debugcore $exitcode "$start_ts"
```

Последствия при `./hlds_run -norestart`:

- без `-debug` — при штатном Ctrl+C в лог печатается «Server crashed, but debug mode is OFF.»;
- с `-debug` — пишется полный `crash_report_*.txt` с «CRASH DETECTED (Exit Code: 130)»
  и «Stop Signal: INT», хотя это остановка оператором.

README (строки 37-38) заявляет обратное: «Чистый выход (код 0 или Ctrl+C) завершает
цикл без отчёта». Верно только для режима с рестартом.

**Что делать:** отфильтровать 130/143 там же, где 0 — либо в `debugcore`, либо до
вызова, единым предикатом «чистый выход» для обоих режимов.

## F2. `MALLOC_CHECK_=3` не работает на современных glibc

**Severity: средняя.** Заявленная защита не включается.

С glibc 2.34 отладочный malloc вынесен в отдельный объект `libc_malloc_debug.so`, и
`MALLOC_CHECK_` / `glibc.malloc.check` действуют только при его `LD_PRELOAD`.

Доказательства с машины проверки:

- glibc 2.44, `libc_malloc_debug.so` присутствует отдельным файлом
  (`/lib64/libc_malloc_debug.so.0`), а не внутри libc;
- тест с переполнением середины кучи: `MALLOC_CHECK_=3 ./mc2` дал вывод, **побайтово
  совпадающий с запуском без переменной** (`munmap_chunk(): invalid pointer`), тогда как
  `LD_PRELOAD=/lib64/libc_malloc_debug.so MALLOC_CHECK_=3 ./mc2` ушёл по другому пути
  диагностики (`free(): invalid pointer`). То же поведение у `GLIBC_TUNABLES=glibc.malloc.check=3`
  без preload.

Затронуто: `hlds_run:98`, шапка (стр. 27-28), README (стр. 72-75) и раздел
«Преимущества перед оригиналом».

**Что делать:** либо добавить preload (`LD_PRELOAD=libc_malloc_debug.so`), либо честно
задокументировать, что реально работает `MALLOC_PERTURB_=170` (`hlds_run:103`) — он в
libc остался и для use-after-free полезнее, чем `MALLOC_CHECK_`. Отдельно учесть, что
`LD_PRELOAD` влияет и на GDB-анализ (дамп придётся разбирать с тем же preload).

## F3. Утечка секретов окружения в отчёт + права файла

**Severity: средняя.** Info-leak с сохранением на диск.

```bash
# hlds_run:211
echo "[*] Environment (engine-related):"; env | grep -E '^(LD_LIBRARY_PATH|MALLOC_|STEAM|TERM|HOME|PATH)'
```

Префикс `STEAM` ловит не только `STEAM_ACCOUNT`, но и `STEAM_PASSWORD`, `STEAM_API_KEY`,
`STEAM_GSLT`. Отчёт `crash_report_*.txt` создаётся через `>>` без изменения `umask`
(обычно 644), т.е. секреты оседают в файле, читаемом всеми локальными пользователями,
рядом с выводами `ps` по всем процессам и списком слушающих сокетов.

README (стр. 53) обещает «переменные окружения движка … без секретов» — не выполняется.

**Что делать:** сузить до явного whitelist нужных переменных (без `STEAM_*` целиком),
маскировать значения и ставить `umask 077` на отчёты и дампы.

## F4. `printf %q` + `script -c` — повторный разбор чужим шеллом

**Severity: средняя.** Портабельность: на Debian/Ubuntu ломает аргументы с кириллицей.

```bash
# hlds_run:120-122
local cmd
printf -v cmd '%q ' "$HL" "${SRV_ARGS[@]}"
script -qec "$cmd 2>&1" "$CAPLOG_FILE"
```

Два независимо проверенных факта:

1. `script -c` исполняет строку через `$SHELL`, а не через `/bin/sh`
   (проверено: при `SHELL=/bin/fish` строку парсил именно fish);
2. `printf %q` в C-локали выдаёт bash-специфичное ANSI-C-цитирование
   (проверено: `Мой сервер` → `$'\320\234\320\276\320\271 \321\201\320\265\321\200\320\262\320\265\321\200'`).

Комбинация: systemd-юнит (`SHELL` не задан → `/bin/sh`, на Debian/Ubuntu это dash) плюс
`LC_ALL=C` (обычно для сервисов) плюс не-ASCII аргумент (`+hostname`, `+sv_password`,
название карты) → POSIX sh не понимает `$'…'` и сервер получит аргумент-мусор.
На машине проверки баг не воспроизвёлся только потому, что `/bin/sh → bash` и локаль UTF-8.
Тот же класс риска: произвольный `$SHELL` (fish старше 4.x не принимает `2>&1` из
`hlds_run:122`).

**Что делать:** не полагаться на ре-парсинг вообще. Положить запуск во временный
launcher-файл с `#!/bin/bash` и `exec "$HL" "$@"`, а в `script` передавать только путь
к нему — тогда строку гарантированно разбирает bash, а не `$SHELL`.

## F5. Typescript в `$TMPDIR` растёт неограниченно

**Severity: средняя.** Эксплуатационный риск на длинной сессии.

```bash
CAPLOG_FILE=$(mktemp)                      # :115
script -qec "$cmd 2>&1" "$CAPLOG_FILE"     # :122
CONSOLE_TAIL=$(tail -n 100 "$CAPLOG_FILE" …)  # :131 — файл удаляется только :132
```

`CAPLOG_FILE` живёт всё время работы сервера и впитывает весь консольный вывод (чат,
логи раундов, спам аддонов). Отчёту нужны только последние 100 строк, а на 24/7 сервере
файл может съесть гигабайты в `tmpfs` (`/tmp`), особенно на VDS с малым RAM.

**Что делать:** либо файл захвата на диске рядом с сервером + ротация, либо опереться на
серверный лог (`log on` / `-condebug` + `tail -F`) вместо pty-типскрипта.

## F6. Гонка с асинхронным systemd-coredump

**Severity: низкая-средняя.** Ложные «no matching dump» на валидных крашах.

```bash
# hlds_run:179
if coredumpctl dump "${HL##*/}" "${since_args[@]}" --output="$systemd_tmp_core" >/dev/null 2>&1 && [[ -s "$systemd_tmp_core" ]]; then
```

`coredumpctl dump` вызывается сразу после завершения процесса, а systemd-coredump
обрабатывает дамп асинхронно: записи в journal в этот момент может ещё не быть. Тогда
отчёт выйдет с «GDB ANALYSIS (SKIPPED)» и предупреждением о неудаче — при том что дамп
есть.

**Что делать:** короткая retry-петля (3-5 попыток с паузой 1 с) либо ожидание появления
записи в `coredumpctl list --since`. Заодно учесть, что матч по `${HL##*/}` неоднозначен,
если на машине несколько инстансов сервера.

## F7. Слишком доверчивый отбор core-файла

**Severity: низкая.** Возможен разбор чужого дампа.

```bash
# hlds_run:152
CORE_FILE=$(find . -maxdepth 1 -type f -name 'core*' -printf '%T@ %p\n' | sort -n | tail -1 | cut -d' ' -f2-)
```

Условия: любой файл в CWD, начинающийся на `core` (чужой дамп, случайный `core_settings.txt`
и т.п.), проверяется только по `mtime` против `start_ts` (`:161`). Более того, если
`kernel.core_uses_pid=1`, имя будет `core.<pid>` — совпадение сохранится, но при
`core_pattern` с суффиксом/префиксом может и не быть.

**Что делать:** дешёвая проверка типа — `file "$CORE_FILE" | grep -q 'ELF.*core'`, плюс
сверка PID, если он есть в имени. Для «файла нет» ветка уже обрабатывается корректно.

## F8. `-timeout 0` проходит валидацию

**Severity: низкая.** Сообщение и поведение расходятся.

```bash
# hlds_run:79
[[ "$2" =~ ^[0-9]+$ ]] || { echo "Error: '-timeout' value must be a positive integer."; exit 1; }
```

`^[0-9]+$` пропускает `0` (и `007`), хотя текст ошибки говорит про «positive integer».
`-timeout 0` даёт плотный цикл рестартов (`sleep 0`, `:317`) с генерацией отчёта на каждый
краш. Верхней границы тоже нет — ничто не мешает вечным 24 ч ожидания.

**Что делать:** `^[1-9][0-9]*$` и, при желании, верхний предел с предупреждением.

## F9. Ротация дампов через `ls | xargs`

**Severity: низкая.** SC2012.

```bash
# hlds_run:276
ls -1t crash_core.*.dmp 2>/dev/null | tail -n +4 | xargs -r rm -f
```

Разбор вывода `ls` ломается на экзотических именах файлов (сейчас имена
`crash_core.<дата>.dmp` безопасны, но ротация вызывается только когда был проанализирован
свежий core и только для файлов `crash_core.*.dmp` в CWD).

**Что делать:** `find . -maxdepth 1 -name 'crash_core.*.dmp' -printf '%T@ %p\n' | sort -rn | tail -n +4 | cut -d' ' -f2- | xargs -r rm -f`
(тот же приём, что уже применён в `hlds_run:152`).

## F10. `log_message … >&2` внутри блока отчёта

**Severity: низкая.** Несогласованность вывода.

```bash
# hlds_run:277 — внутри блока, который пишется в файл (…} >> "$CRASH_LOG_FILE", :286)
log_message "Old core dumps rotated (kept 3 newest)." >&2
```

Единственная строка, уходящая в терминал, тогда как окружающий текст идёт в отчёт;
печатается даже если ротировать было нечего.

**Что делать:** либо убрать `>&2` (в отчёт, как соседние `echo`), либо перенести вызов
из блока и печатать только при фактической ротации.

## F11. Пять запусков gdb на один дамп + хрупкая связка массивов

**Severity: низкая.** Стоимость и устойчивость.

GDB-анализ (`hlds_run:237-265`) разбит на пять секций, каждая — отдельный запуск
`gdb -batch` со своим `mktemp`-файлом команд. Плюсы (читаемость отчёта, отсутствие
heredoc-эскапирования) очевидны, но:

- ядро грузится пять раз; для дампа в несколько ГБ это заметное время и повторный расход
  памяти, тогда как раньше был один batch;
- `section_names` и `section_cmds` (`:237-254`) обязаны совпадать по длине и порядку —
  проверки нет, при расхождении секция молча выйдет пустой или с чужой командой;
- `local -i sec; for sec in "${!section_names[@]}"` итерируется по индексам имён, а не
  команд.

**Что делать:** если цена загрузки критична — вернуть один batch с `echo`-заголовками
между блоками (метки секций можно печатать из самого командного файла gdb). Связку массивов
заменить на одну структуру «имя + команда», чтобы рассинхрон был невозможен.

## F12. Мелкие замечания по надёжности и диагностике

- **`ulimit -c unlimited` может не сработать** (hard limit 0 в контейнере/под systemd):
  ошибка не проверяется, и отчёт молча выйдет с «GDB ANALYSIS (SKIPPED)». Стоит на старте в
  `-debug` предупреждать, если `ulimit -c` == 0 или `kernel.core_pattern` — pipe, а
  `coredumpctl` недоступен (`:95`, `:174`).
- **`dmesg` и `ss -p` под non-root** (`:216-218`) пишут строки своих ошибок прямо в тело
  отчёта. Косметика; при желании глушить в `/dev/null` с пометкой «недоступно».
- **gdb без `-nx`** (`:263`): пользовательский `~/.gdbinit` влияет на анализ дампа.
- **`-binary <path>`**: отчёт всё равно подписывает хеш как «Binary checksum (hlds_linux)»
  (`:212`), а `coredumpctl dump "${HL##*/}"` (`:179`) матчит по имени — см. F6.
- **Код 130/143 неразличим по источнику**: if сервер убит извне `SIGINT`, в рестарт-ветке
  это (`:300`) будет воспринято как чистый выход. Для диагностики полезно логировать
  «остановлено оператором/сигналом».
- **`set -o pipefail` без `set -e`** — безопасно: проверено, что пайплайн в `:131` с
  ненулевым статусом `grep` не роняет скрипт (статус назначения нигде не проверяется).

## Проверено — работает как заявлено

- `bash -n` — синтаксис чистый; CRLF нет, файл ASCII.
- `script -e` действительно прокидывает код выхода: SIGSEGV → `139`, `exit 130` → `130`.
- `script` при получении INT/TERM сам убивает ребёнка («Session terminated, killing
  shell...») — осиротевшего сервера не остаётся; README в этой части прав.
- Ловушки корректны: `cleanup_temp` на `EXIT` + маршрутизация `INT`/`TERM` через `exit`,
  временные файлы (`CAPLOG_FILE`, `GDB_CMDS_FILE`, каталог systemd-дампа) подчищаются на
  любой ветке выхода.
- GDB-командники создаются через `mktemp` (`:260`) — гонки на фиксированном имени нет.
- Имена отчётов и дампов с наносекундами — два краша в одну секунду не перезапишут друг друга.
- Хвост консоли чистится от `\r`, ANSI-последовательностей и аннотаций `script` (`:131`).
- Разбор аргументов строгий: скриптовые флаги серверу не утекают, отсутствие значения и
  нечисловой `-timeout` — жёсткая ошибка (`:75-84`).
- Логика crash-loop корректна: счётчик сбрасывается при аптайме ≥ `HEALTHY_UPTIME`,
  «чистый» выход (0/130) прерывает цикл (`:300-317`).
- `swapinfo`, `ps`, `df`, md5-суммы `.so` — команды безобидные, вывод в отчёт не течёт за
  пределы задуманного.

## Гигиена репозитория (вне скрипта)

## Приложение: как воспроизводились проверки

```bash
bash -n hlds_run
shellcheck -s bash hlds_run

# script -c исполняет строку через $SHELL
SHELL=/bin/fish script -qec 'echo hi' /dev/null          # парсит fish

# %q в C-локали -> ANSI-C-цитирование (не понимает dash)
LC_ALL=C bash -c 'printf "%q\n" "Мой сервер"'

# проброс кода выхода при сигнале
SHELL=/bin/sh script -qec 'kill -SEGV $$' /dev/null; echo $?   # 139

# MALLOC_CHECK_ без preload = no-op (glibc >= 2.34)
gcc -O0 -w -o mc2 mc2.c        # переполнение середины кучи
./mc2; echo $?                                             # 134, нативный путь
MALLOC_CHECK_=3 ./mc2; echo $?                              # 134, вывод идентичен
LD_PRELOAD=/lib64/libc_malloc_debug.so MALLOC_CHECK_=3 ./mc2; echo $?  # 134, другая диагностика
```

## Приоритеты

1. **F1** — убирает ложные «краши» на штатном Ctrl+C в `-norestart`.
2. **F4** — делает запуск независимым от `$SHELL` и локали (единственная находка,
   способная привести к мусорным аргументам сервера).
3. **F3** — закрывает утечку секретов и права на файлы отчётов.
4. **F2 / F5** — приводят заявления README в соответствие с реальностью и снимают
   эксплуатационный риск на долгой сессии.
5. **F6-F12** — плановые улучшения надёжности и косметика.
